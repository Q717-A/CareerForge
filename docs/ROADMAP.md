# CareerForge Roadmap

## 开发与验证原则

CareerForge 按“小步实现 → 验证 → 再推进”开发，不把多个尚未跑通的模块一次性堆上去。

每个功能切片至少经过四个闸门：

1. **数据层**：模型、迁移、旧数据/旧备份兼容；
2. **后端层**：核心规则单测 + API 冒烟 + 跨模块关联测试；
3. **前端层**：类型契约、页面交互测试、构建/格式/lint；
4. **闭环层**：从用户入口走到最终结果的手工冒烟，确认错误状态也能正确回退。

只有上一层通过，才进入下一层。CI 没有实际运行时只能标记为“已实现、待验证”，不能写成“已完成”。

详见 [VERIFICATION_CHECKLIST.md](VERIFICATION_CHECKLIST.md)。

## V1 — Foundation

目标：把 ResumeForge fork 正式变成 CareerForge，并建立后续不会推倒重来的数据边界。

- [x] 建立独立开发分支；
- [x] 明确 CareerForge 产品愿景与事实红线；
- [x] 建立 Project Lab 后端数据模型和基础 CRUD；
- [x] 建立项目状态闸门；
- [ ] 增加 Project Lab 前端页面；
- [ ] 把 Project Lab 接入功能目录与助手能力地图；
- [ ] 增加 Truth Engine 五级事实状态；
- [ ] 为 Project Lab 增加“转为事实台账草稿”的显式动作。

### Project Lab 状态链

```
proposed → learning → implemented → verified → resume_ready
   建议       学习中       已实现        已验证       可写入简历
```

规则：

- 不允许一次跳过多个阶段；
- 可以主动退回较早阶段重新学习/修改；
- 进入 `verified` 前必须有证据和结果总结；
- 进入 `resume_ready` 前必须补齐掌握说明、简历表述和面试追问准备。

## V1.1 — Truth Engine

- [ ] VERIFIED / REFRAMED / INFERRED / LEARNING / UNVERIFIED；
- [ ] 简历句子与事实台账建立可追踪引用；
- [ ] 数字成果、公司、学校、项目名、技术栈采用更严格的生成闸门；
- [ ] UNVERIFIED / LEARNING 默认禁止进入最终导出；
- [ ] AI 对任何“新数字”必须给出证据来源或明确标记待确认。

## V1.2 — Role-specific Resume Tailor

- [ ] 从 JD 提取硬性条件 / 核心能力 / 加分项 / 证据要求；
- [ ] 针对岗位选择最相关事实；
- [ ] 同一事实生成机械设计版 / CAE 版 / 自动驾驶测试版 / AI 版等不同表述；
- [ ] 输出“删了什么、为什么删；强调什么、为什么强调”的修改说明；
- [ ] 每个岗位保留独立简历版本。

## V1.3 — Job Radar

- [ ] 搜索配置：岗位、城市、学历、薪资、校招/社招等；
- [ ] 公司官网 / 公开 ATS 优先；
- [ ] 招聘平台浏览器辅助采集；
- [ ] 多来源去重；
- [ ] 人工勾选后才进入正式岗位库；
- [ ] 定时采集放在后续阶段，不在 V1 默认后台运行。

## V1.4 — Project Lab Agent

- [ ] 从真实岗位缺口自动生成项目建议；
- [ ] 项目拆成知识点、里程碑、代码、实验、证据、结果；
- [ ] 自动生成“我应该真正掌握什么”的检查清单；
- [ ] 生成面试追问树；
- [ ] 只有通过验证的项目才能转为事实台账草稿；
- [ ] GitHub 仓库、实验截图、报告等成为证据来源。

## V2 — Career Feedback Loop

- [ ] 一岗一档：JD → 分析 → 简历 → 投递 → 面试 → 结果；
- [ ] 比较哪些简历版本获得更多后续反馈；
- [ ] 识别反复出现的能力缺口；
- [ ] 根据历史结果调整 Job Radar 和 Project Lab 优先级。

## 暂不优先

- 完全无人值守自动投递；
- 绕过验证码、登录保护或招聘网站风控；
- 为了 ATS“评分”而制造虚假关键词；
- 自动生成无法被用户讲清楚的“包装项目”。
